# 老有樹 — 家庭聚會平台規格（family_gather.md）

> 本文件記錄「家庭聚會」tab（#/family-gather）嘅產品決定與規格，係家庭聚會功能嘅「產品憲法」。
> 與 merchant_platform.md（商戶端底層）、product_decisions.md（用戶端）並列，三者不可互相矛盾。
> 標示：【核心】貫穿全局嘅定位／【已定】方向確認／【待定】需將來拍板／【願景】長遠 v2+ 方向。
>
> ⚠️ 本文件所載一切內容，以 Core Document v4 第四節（家庭聚會平台）為最高依據；如有出入，以 Core Document 為準。

---

## 〇、定位與核心原則【核心】

【核心】「家庭聚會」係老有樹商戶平台嘅**情境入口（context-driven entry）**，並非獨立商戶系統。與「我的推薦」(#/my-recommend) 共用同一個商戶資料庫（`merchant` 表）、同一套上架准入（`is_listed`）、廣告層級（`ad_tier`）及贊助標示規則。兩者分別在於**入場方式**：

| Tab | 入場方式 | 用戶心態 |
|-----|---------|---------|
| 我的推薦 | 主動瀏覽、按分類／地區搵附近商戶 | 「我想搵一間 X」 |
| 家庭聚會 | 由重要日子／節日場景帶入，按場合過濾商戶 | 「快到 XX 生日，我想安排」 |

【核心】平台本質為**展示 + 引流平台**，成交永遠喺 app 之外發生。平台不掂交易金流、不抽佣、不介入商戶與用戶之間任何交易（沿用 Core Document 第八節第一條「刻意永久劃出去嘅界線」）。

【核心】所謂「訂餐廳／訂蛋糕／買禮物」意向掣，**唔係下單付款**，而係「跳去相關商戶列表 + 一鍵聯絡（打電話／WhatsApp／導航）」。真實訂購交易屬第三層，明確不做（見第九節）。

## 一、與 merchant_platform.md 嘅復用關係【核心】

【已定】家庭聚會**不新建商戶 schema**。所有商戶資料、地區三級層級（區／地區／地標）、主分類與子標籤、`is_listed`／`ad_tier`／贊助佈局，一律復用 merchant_platform.md 所定結構。

【已定】家庭聚會相對「我的推薦」只新增以下邏輯，不觸碰商戶底層：
1. **場景 → 商戶分類映射**（按場合過濾出相關商戶，見第三節）
2. **聚會發起 + 家庭圈邀請卡**（見第五節；含聚會協作 schema，屬家庭聚會自有實體，與 merchant 表分離）
3. **優惠券雙動作流程**（claim + WhatsApp 確認，見第六節）

【核心】贊助標示原則完全沿用 merchant_platform.md §3.2／§3.3：家庭聚會列表內任何受 `ad_tier` 影響嘅靠前／置頂位置，必須以「贊助／Sponsored」明確標示，與自然排位清晰區分。此原則不可妥協。

【已定】排序基礎沿用 merchant_platform.md：自然排序以「距用戶選定地標距離」為準；ad_tier 2 置頂區塊 > ad_tier 1 靠前 > ad_tier 0 自然名單。

## 二、入口來源【已定】

【已定】家庭聚會共有三個入口，全部指向同一個 tab：

1. **底部 tab bar**：家庭聚會為基本四 tab 之一（家庭樹／家庭圈／家庭聚會／我的推薦），沿用 Core Document 第六節。
2. **重要日子提醒卡「去安排」行動**：家人喺家庭圈提醒卡或事件詳情頁撳「去安排（禮物／聚會／活動）」，帶場合參數跳入家庭聚會，並自動套用該場合嘅場景過濾（見第三節）。此為 product_decisions.md v1.2〔提醒卡流程〕已定之連接點。
3. **公眾節日推送**：節日臨近時全平台推送，帶入相關節日聚會商戶列表（沿用 Core Document 3.4）。

【核心】入口 2、3 於**忌辰場合一律不提供任何商業意圖行動**，強制走莊重分支（見第七節）。

## 三、三層結構與按場景過濾【已定】

### 3.1 三層結構（沿用 Core Document 3.4）

| 層級 | v1 狀態 | 內容 |
|------|--------|------|
| 第一層 | 【已定 v1 做】 | 提醒 + 一鍵祝福／留言，純溫度、零商業。此層屬家庭圈／提醒卡範疇，家庭聚會不重複。 |
| 第二層 | 【已定 v1 做】 | 意向掣帶用戶去相關商戶列表 + 一鍵聯絡（打電話／WhatsApp／導航）。**此為家庭聚會 v1 核心。** |
| 第三層 | 【願景 / future backlog，明確不做】 | 真實訂購交易系統（下單、付款）。永久劃出 v1（Core Document 第八節第三條）。 |

### 3.2 場景 → 商戶分類映射【已定 / 映射表待業務確認】

【已定】家庭聚會按「場合類型」過濾出相關商戶主分類，語氣與意向選項因場合而異（沿用 Core Document 3.4）：

| 場合類型 | 語氣 | 意向 → 過濾商戶分類（示例） |
|---------|------|--------------------------|
| 生日（人） | 歡樂 | 訂蛋糕 → 飲食（蛋糕）／訂餐廳 → 飲食（酒樓）／買禮物 → 禮品與花藝 |
| 生日（寵物） | 歡樂 | 寵物蛋糕／寵物用品／寵物 friendly 餐廳（分類待補，見待定 3） |
| 結婚週年（金／銀婚） | 溫馨儀式感 | 訂餐廳 → 飲食／訂鮮花 → 禮品與花藝 |
| 里程碑（入學／畢業等） | 祝賀 | 訂餐廳／買賀禮 |
| 公眾節日 | 節日主題 | 節日聚會餐廳／節日禮盒／鮮花 |
| **忌辰** | **莊重懷念** | **獻花意向 → 只限鮮花／拜祭；嚴禁其他（見第七節）** |

【待定】上表為 Core Document 語意之落地示例；「意向 → 商戶分類」精確映射清單須經業務團隊確認（見待定 1）。

## 四、用戶端功能（v1）【已定】

【已定】家庭聚會用戶端 v1 提供：
- 服務分類瀏覽（節日聚會、生日宴、蛋糕、鮮花、禮物、聚會場地、寵物相關服務等）
- 商戶／服務展示頁（相片、介紹、地址、營業時間、電話、簡單服務內容）
- 由重要日子／公眾節日直接跳入相關商戶列表（帶場景過濾）
- 接觸商戶方式（**不含交易**）：一鍵打電話、一鍵 WhatsApp、一鍵睇地圖／導航

【已定】上述接觸掣復用「我的推薦」已實作之欄位與行為：`phone`（打電話）、`whatsapp`（WhatsApp，null 隱藏）、`map_url`（導航，null 隱藏）。無需新增商戶欄位。

## 五、聚會發起、投票揀日期、家庭圈邀請卡【已定 / 分階段落地】

【已定 / 目標】家庭聚會 v1 之完整目標為多人協作聚會：**發起聚會 → 邀請家人 → 投票揀日期 → 確認 → 自動生成家庭圈邀請卡**。此為本 spec 之設計終點，schema 一次過設計妥當。

### 5.1 分階段落地（⚠️ 受 SSO 限制）

【核心 / 技術現實】截至本版，家庭樹**尚未有真正多用戶登入（SSO）**。後端 `functions/api/_currentMember.ts` 明言為「第一版臨時方案：用當前 family 的 `is_self = 1` 成員頂住登入用戶」——即系統目前**無法辨識個別家人身份**，任何裝置打開皆被當作同一個 `is_self` 成員。

【已定】因此聚會功能分兩階段落地：

| 階段 | 內容 | 前置條件 |
|------|------|---------|
| **階段一（SSO 前，可即做）** | 發起聚會、設定場合、加入候選日期、確認最終日期地點、自動生成家庭圈邀請卡。發起與確認皆由 `is_self` 成員操作。 | 無（現有基建足夠） |
| **階段二（待 SSO 解鎖）** | 邀請個別家人、逐人投票揀日期、RSVP（出席回覆）。因需辨識「邊個家人投咗票」，須待 SSO 落實方可實作。 | CoEldery 85 會員 SSO（JWT）接通，`_currentMember` 改為真身份 |

【核心】階段二嘅 schema **v1.1 一次過設計好**（見 5.3），但投票／RSVP 之寫入 API 與 UI **SSO 前不實作**；SSO 一到，只需接上真身份即可解鎖，無需改動資料結構。此設計避免造出「無法辨識投票人、票數失真」嘅假投票功能——後者違反 Core Document「私密為先、後端權限嚴格」之設計信念。

### 5.2 家庭圈邀請卡（階段一即做）

【已定】當聚會之日期與地點確認後，系統自動喺**家庭圈**生成一張「聚會邀請卡」（沿用 Core Document 3.4）。內容：
- 場合（如「爸爸 80 大壽」）
- 日期時間
- 商戶名稱／地址／相片（取自 `merchant` 表）
- 一鍵導航（`map_url`）／一鍵致電（`phone`）

【已定】邀請卡雙重價值：對家人係清楚嘅聚會通知；對商戶係額外免費曝光。

### 5.3 聚會協作 schema 設計【已定 / 待實作時定案】

【已定 / 方向】聚會屬家庭聚會自有實體，與 `merchant` 表分離，初步設計三張表（欄位細節待實作 spec 定案）：

- **`gathering`**：聚會主體。含 `id`、`family_id`、發起人 `initiator_member_id`、場合類型 `occasion_type`、關聯對象成員 `subject_member_id`（可空）、關聯商戶 `merchant_id`（可空）、最終確認日期 `confirmed_date`（可空）、狀態 `status`（草擬／投票中／已確認／已取消）、`created_at`。
- **`gathering_date_option`**：候選日期。含 `id`、`gathering_id`、候選日期 `option_date`。
- **`gathering_vote`**（⚠️ 階段二，SSO 後啟用）：投票／RSVP。含 `id`、`gathering_id`、`option_id`、投票成員 `voter_member_id`、回覆 `rsvp`（出席／不出席／未定）。SSO 前此表不寫入。

【待定】上述欄位、狀態機、名額與截止邏輯，於實作 spec 階段最終定案（見待定 2）。

## 六、優惠券雙動作流程（統一 coupon engine）【已定框架 / 細節待 spec】

【已定】家庭聚會與推薦系統共用**同一套 coupon engine**，支援多 type，共用底層機制（發券、領取、WhatsApp 聯絡商戶、商戶自行核銷、記錄，全程不涉平台金流）。

【已定】v1 兩個 type（沿用 Core Document 3.5、第四節）：
- **Type A 家庭聚會推廣券**：商戶買嚟做營銷，會員限量領取，製造稀缺感。
- **Type B 推薦獎勵券**：專為推薦獎勵而設，成功推薦 5 位家人解鎖後可喺清單自選。

【已定】雙動作流程：
1. **領取（Claim）**：記錄會員身份、商戶、券別、時間，受限量控制。平台掌握「領取」記錄。
2. **一鍵 WhatsApp 確認預訂**：訊息預填會員身份及券資訊，直接發送俾商戶。商戶掌握「預訂確認」記錄。

【已定】兩邊記錄夾埋完成核銷；此雙動作亦提供最高質引流證據（真實預訂 lead）。

【待定】名額鎖定／釋放邏輯、核銷方式（coupon code／QR）、coupon DB schema、有效期、一次性 vs 常設——與 merchant_platform.md §四待定 6 統一處理，避免重複定義（見待定 5）。

⚠️ 注意：coupon 之「領取」亦需辨識會員身份，與投票同受 SSO 限制；SSO 前 coupon 領取記錄同樣只能歸於 `is_self` 成員。此依賴於待定 5 一併處理。

## 七、忌辰硬攔截【核心 / 零容忍】

【核心】忌辰場合之商業限制，逐字沿用 product_decisions.md〔家庭日曆提醒呈現方式〕及 merchant_platform.md §5.2，不得以任何家庭聚會或商戶廣告邏輯覆蓋：

> **忌辰特別規則：永不彈出。只用安靜、莊重嘅提示，零商業意圖（只容許鮮花／拜祭意向，不可訂蛋糕／餐廳等）。**

【核心】具體禁止行為（家庭聚會角度）：
- 忌辰場合進入家庭聚會，**不得出現任何商戶廣告、贊助位、聚會發起、投票、訂購／聚會／慶祝按鈕**。
- 忌辰「去安排」只限「獻上思念／送上鮮花」等莊重選項。
- 即使商戶主分類為「殯儀與身後事」或「禮品與花藝」，亦不得**主動推送**至忌辰場合；如用戶主動搜尋則另計（邊界見待定 4）。

【核心 / 技術硬守則】任何場景過濾、商戶推薦或聚會發起邏輯，須在觸發前**先判斷當前場合是否為忌辰**；確認為忌辰則強制跳過一切商業內容及聚會發起，走莊重分支。此判斷須早於一切 `ad_tier` 排位、coupon 及聚會邏輯。

## 八、與推薦飛輪嘅咬合【已定 / 願景協同】

【已定】家庭聚會、我的推薦、推薦獎勵三者咬合成自我強化飛輪（沿用 Core Document 3.5）：
長者為攞券而推薦家人 → 家庭樹增長 → 攞 Type B 券去家庭聚會幫襯商戶 → 商戶見真實引流、更肯出券出廣告費 → 平台有更多更靚嘅券 → 長者更有動力推薦。

【已定】引流數據（邊個商戶幾多人睇過／撳打電話／撳 WhatsApp／領券）v1 建好但屬內部用途，暫不對外使用，待數據成熟先作與商戶傾廣告費之硬證據（沿用 Core Document 第四節）。

## 九、Out of Scope（v1 不做）【已定】

| 項目 | 原因 / 依據 |
|------|------------|
| App 內金流／用戶付款／第三層真實訂購交易 | Core Document 第八節第一、三條，永久界線 |
| 平台通用券／預售券 | 涉金流、退款、可能觸及 SVF 儲值支付牌照（Core Document 第八節第二條），入 future backlog |
| **逐人投票揀日期／RSVP 之實際寫入與 UI** | ~~技術上依賴 SSO 辨識個別家人；SSO 前不實作~~ **→ 2026-09-10 已實作**：per-member 登入（`member_auth` + `family_session`，見 v1.3）令每位家人各自有身份，逐人投票／RSVP 已落地（見第五節、v1.3）。 |
| 商戶評分／評論 | 沿用 merchant_platform.md §六 |
| 商戶 vs 用戶即時通訊 | 接觸只限電話／WhatsApp／導航 |
| 消費兌換額度機制 | Core Document 第八節第四條 |
| coupon 核銷追蹤自動化 | 依賴後台 UI，v1 線下核銷 |
| 商戶廣告自動插入家庭圈 feed | merchant_platform.md §5.1，強插破壞情感氛圍 |

## 十、待定清單

1. **場景 → 商戶分類精確映射**：各場合對應哪些主分類與子標籤，須業務團隊確認。
2. **聚會協作 schema 定案**：`gathering` / `gathering_date_option` / `gathering_vote` 欄位、狀態機、投票截止與名額邏輯，於實作 spec 階段最終定案。
3. **寵物相關商戶分類**：寵物蛋糕／用品／friendly 餐廳是否新增為 merchant_platform.md 子標籤，抑或歸入現有分類？
4. **忌辰「用戶主動搜尋」邊界**：與 merchant_platform.md §待定 8 一致——主動搜尋殯儀商戶時是否豁免忌辰限制？
5. **coupon engine 全套細節**：名額鎖定／釋放、核銷方式、DB schema、有效期（與 merchant_platform.md §待定 6 統一處理）。
6. **邀請卡於忌辰場合之處理**：忌辰不生成聚會邀請卡——是否另設「思念卡／獻花卡」莊重版本，抑或忌辰完全不進家庭聚會流程？
7. **場景參數傳遞格式**：提醒卡「去安排」跳入家庭聚會時傳遞哪些參數（場合類型、對象成員 id、日期），介面契約待與 product_decisions.md 提醒卡流程對齊。
8. **共用 API 查詢參數**：是否於現有 `/api/merchants` 加 `scene`／`category` 過濾參數，抑或另開 endpoint？（實作前須讀 merchants.ts 確認。）
9. **SSO 落實時序**：階段二（投票／RSVP／coupon 領取歸屬）全數依賴 CoEldery 85 會員 SSO；SSO 落實時序須與主程式（85AI）團隊對齊。
