# CoAppery AI 協作開發流程 SOP

## 目的

規範「人與 AI（對話助手 + Genspark Code 等）如何合作開發系統」。此 SOP 管「人同 AI 點合作」，與《模組化開發 SOP》（管「code 點組織」）並行。兩者加埋，方為完整的 CoAppery 開發方法。

---

## 最重要的覺悟（全文核心）

**本 SOP 由「人 + 流程」強制執行，不假設 AI 會自動遵守。**

AI 沒有持續記憶，亦不會自我約束。每次只會盡量滿足當下 prompt，寫住寫住就會偏離規範、將本應抽出的片段塞回頁面、愈滾愈大。因此，任何規範若只寫在文件、期望 AI 自動跟足，必然失敗。CoAppery 的解法是：由人畫好邊界、由可驗證指標（行數、grep、build）把關、由細步 commit 做保險。AI 只是照圖施工的工人，不是判官。

---

## 四大核心動作

**動作一：先固化「不變的真相」，再郁 code。** 開工前，必須將 Core Document（產品定義）、設計規範、rules.md、SOP 全部存入 repo（memory_vault），作為整個專案的「憲法」。之後每一步，人與 AI 都以此為依據，不得憑當下對話重新理解需求。此舉杜絕 AI 逐次漂移。

**動作二：細步進行，每步留證據。** 不得一次過「起成個 app」。工作拆成可一眼看完的細步（如 3a、3a-fix、fix-2…），每步必須產出：commit hash、變更檔案清單、grep 驗證、build 結果、build log 記錄、deploy preview。細步 + 證據 = 隨時可驗證、可回退。

**動作三：AI 不得自行拍板，每個決定由人 sign off。** AI 的職責是「分析、列選項、給傾向、執行」，不是「決定」。凡涉及產品、設計、規則的取捨（如改色、改名、行數上限），AI 須列出問題與選項並停低，等人確認後方可執行。

**動作四：睇得見先算數。** grep 與 build 通過，不代表視覺正確。每步完成後必須 deploy preview，由人肉眼在手機 + 桌面兩邊核實。凡 grep / build 驗不到的問題（排版重疊、卡片闊度、桌面拉散等），一律以肉眼 preview 為準。

---

## 標準工作循環（每一細步）

**第一步，定義細步：** 由對話助手將任務拆成一個「可一眼看完、可驗證」的細步，寫清楚範圍與禁區（不加互動 / 不改 props / 不入新套件等）。

**第二步，出 prompt：** 對話助手產出自足的 Genspark prompt，包含任務、參考檔案、明確禁區、完成後必須回報的證據項（commit、grep、build、preview）。

**第三步，人手確認：** 人 review prompt，確認範圍合理、禁區清楚，方可交 Genspark 執行。

**第四步，Genspark 執行並回報證據。**

**第五步，驗證證據：** 對話助手核對 grep / build / props / build log；若報告只寫「完成」而無實際證據，須退回要求補交。

**第六步，deploy preview + 肉眼核實：** 人在手機 + 桌面核實視覺；列出 OK 與待修項。

**第七步，決定下一步：** 全過則收貨、進下一細步；有問題則出 fix prompt，重複循環。

---

## 把關指標（機器可驗證，唔靠 AI 自覺）

每步收貨前，以下指標須全綠，任何一項不過即打回頭，不得放行：

**行數閘：** wc -l 檢查 page 檔 ≤ 200 行、module 檔 ≤ 250 行（依模組化 SOP 規則 B）。

**禁用內容閘：** grep 硬編色（rgba）、粵語禁用字、writing-mode 等，結果須符合預期。

**Build 閘：** npm run build 零錯誤。

**相容閘：** 共用件 props interface 未變（向下相容）。

**證據閘：** commit hash、build log、preview URL 齊全。

---

## 失敗回退機制

因細步 + 每步 commit，一旦某步 AI 又將 code 滾大、或引入難修的 bug，不必勉強救：直接 git 回退至上一個 commit hash，重出一個更嚴格的 prompt（明確禁止上次出錯的行為）。此機制將「AI 漂移」的代價，由「整個專案報廢」降至「一步重來」。

---

## 角色分工

**人（owner）：** 定義產品、拍板決定、肉眼核實、按閘放行或打回。

**對話助手：** 固化真相、拆細步、畫積木邊界、出 prompt、核證據、列選項給傾向。

**Genspark Code：** 照圖施工 —— 依 prompt 與積木分解清單寫 code，回報證據。不自行決定架構或產品取捨。

---

## 與其他規範的關係

本流程 SOP 與《模組化開發 SOP》、rules.md 並行。三者關係：rules.md 管內容與語體，模組 SOP 管 code 結構，本流程 SOP 管人機協作。任何衝突，以較嚴格者為準。

---

## 修訂機制

本 SOP 為活文件。實戰中若發現規則過緊（阻礙開發）或過鬆（擋不住 bug），應予修訂。修訂由對話助手產出修訂 prompt、更新本文件、記入 build log，並於下方「修訂記錄」表補一行（日期 / 修改內容 / 原因）。
