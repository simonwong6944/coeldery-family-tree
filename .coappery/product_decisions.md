老有樹 — 產品決定紀錄（product_decisions.md）
本文件記錄產品層面嘅決定與願景,係將來寫 code 前嘅「產品憲法」。 與 rules.md（技術規範）分工:rules.md 管「點寫」,本文件管「做乜、點解」。 標示:【核心】貫穿全局嘅定位 /【已定】方向確認 /【待定】需將來拍板 /【願景】長遠 v2+ 方向。

〇、核心定位【核心】
老有樹係一個平台 / 工具,並非用戶相片嘅擁有者或永久保管人。相片由用戶自行上傳,平台嘅價值在於「幫佢哋更好地組織回憶 + 讓一家人一同觀看」。平台不會「刪除用戶嘅相片」——所謂過期 / 封存,僅指平台不再托管呈現,相片正本始終屬於用戶(故提供免費下載)。此定位貫穿以下所有保存 / 過期 / 封存 / 傳承決定。

一、上傳與相簿權限
【已定】相簿屬於相簿主人,配額計主人。 【已定】其他家人可幫主人上傳相片,方便長者或無能力自行上傳者（如寵物）。 【已定】主人保留最終控制權（可保留 / 可刪 / 或需批准）。 【待定】批准機制細節（自動入相簿定要主人 approve）留待接後端定。 【已定】Mockup 階段每個成員頁照擺上傳按鈕,權限邏輯待實作。

二、相簿架構（只有一個相簿）
【已定】全 app 只有一個相簿,即「成長相簿」（註：v1.3 後，「一個相簿」指底層單一儲存；顯示層按「每樹顯示位」+ 可見性呈現，本人自睇為全部，見下方 [決策] 相簿配額。）
;不設獨立嘅「普通相簿」。加相入相簿 = 加入成長相簿。 【已定】成長相簿定位:「精選人生時間軸」,回應「日日影幾百張、冇人整理」痛點,對長者尤具情感價值。 【已定】人人皆有嘅標準功能,一視同仁——不因年齡或物種特別標示或條件顯示。每個成員（含寵物）B2 頁固定有此區塊。 【已定】配額:每月 5 相 + 2 片。（⚠️ 綁人講法已由 v1.3「每樹顯示位」決策取代——現行為每棵樹各 5+2 顯示位，詳見下方 [決策] 相簿配額改為「每樹顯示位」。此處僅存歷史。）【已定】涵蓋範圍:由出生到離世,永久免費、不過期（核心免費價值）。 【已定】輸入方式:月曆式,相片掛喺對應月份;睇相簿時呈現由舊到新嘅時間軸。 【已定】支援補錄舊相:可將以前舊相放入,掛返對應月份。 【待定】單月上限對「補錄舊相」是否放寬。 【已定】流向:相片加入成長相簿時,會自動同步出現喺家庭圈動態（單向）;喺家庭圈隨便 post 嘅相,不會自動入成長相簿（除非特登揀）。

三、家庭圈動態
【已定】全 app 只有一個家庭圈動態頁,不設第二個動態頁。 【已定】家庭圈動態無數量配額,想 post 幾多都得;內容包含相片、文字、描述、回應、留言等互動脈絡。 【已定】動態預設保留 12 個月,過期後連相清走（控制儲存成本;體現平台定位——平台不永久托管,相片正本用戶自持）。 【已定】提供「下載全部 / 選定相片到裝置」功能,免費、隨時（尊重用戶對自己回憶嘅擁有權;亦作過期前自救）。 【待定 / UX】過期處理須溫柔:過期前多次提醒（「呢啲相仲有 X 日,想留低請下載,或揀入成長相簿永久保存」),避免長者誤以為系統故障或回憶被奪。 【已定】B2「查閱動態」卡 = 前往家庭圈 + 自動篩選淨係呢個人嘅動態（同一條路,預設幫用戶篩好）。 【已定】寵物頁不設「查閱動態」卡（寵物不能發動態 / like / 留言）。

四、商業模式
【已定】方向:Freemium（基本免費 + 增值收費）。 【已定】免費核心:家庭樹、家庭圈動態、成長相簿（出生到離世,每月 5+2,永久保存）。 【已定】收費原則:只為「老有樹自家提供嘅服務」收費;不向商戶抽佣、不向長者硬銷。 【已定】增值收費項: 　- 成長相簿配額提升（每月 5+2 → 更多，如 10+4）。（⚠️ v1.3 明確：升級為 per tree 提升某棵樹之每月上限，非買總額；「一人屬多棵樹自然多額」不視為增值、不收費。） 　- 家庭圈動態延長保留 / 永久（「更多年份」)。 　- 印製實體相冊 / 相書寄到屋企。 【已定】並無限制家庭成員數目。 【已定】放棄「兌換 / 積分解鎖」方向（對長者過於複雜）;兌換概念可留作免費推廣手段（如介紹新家庭送額外容量）。 【洞察】付費者可能係中年子女而非長者本人;定價 / 包裝可朝「送畀父母嘅禮物」方向。 【待定】實體相書由合作印刷公司做 fulfillment;須釐清對方係「供應商」（你付費、佢代工）定「贊助」（提供資源、換取曝光等）,性質不同,合作前講清。 【待定 / 矛盾提醒】rules.md 現時「嚴禁付費 / 交易 UI」;將來實作收費功能時需修訂並處理此矛盾。

五、不活躍家族處理【待定 / 部分已定】
【已定】判斷單位係整個 family tree,而非個別用戶。只要家族內仍有任何成員活躍,所有成員（含已離世長輩）相簿一律保留。 【已定】原因:離世長輩之相簿對在世家人有懷念價值,不應因長輩本人無活動而刪除——此正係產品核心情感場景。 【已定】觸發條件:整個 family tree 連續 12 個月零活動（全家無人登入 / 更新）。 【建議】採階梯式處理:多重溫柔提醒（email/SMS 通知全家）→ 長寬限期 → 封存（移冷儲存,非即時永久刪除)→ 極長期無反應才考慮徹底刪除。呼應核心定位:平台停止托管 ≠ 刪除用戶資產。 【待定】封存 / 刪除嘅具體時序與復原機制。

六、產品願景【願景 / v2+】
跨世代家庭樹
家庭樹可跨世代延續,不因一代離世而終結。
頂代全部離世後,樹仍保留他們;焦點 / 主位自動移至在世且活躍嘅世代,後代往上 scroll 可瞻仰、懷念先人（僅供觀看）。
呼應華人「慎終追遠」文化,賦予產品傳世價值。
與保存規則協調:只要家族仍有後代活躍,整棵樹（含先人）永久保留。
離世狀態與世代推移機制（機制方向已定,實作屬 v2+）
家庭樹提供輸入成員「離世日期」嘅位置。
世代推移完全由家人主動輸入觸發,系統絕不自行推斷或假設離世。
當某世代全體成員皆被輸入離世日期 → 焦點自動下移至在世世代;先人保留頂部供瞻仰。
若家人未輸入 → 系統不作任何假設,該世代維持原位（「唔填唔關平台事」)。
確保系統永不擅自宣告離世或更動家庭樹,符合平台定位。
傳家訊息 / 遺言【最需慎重】
成員可留下指定給後代嘅訊息;可為文字 / 相 / 影片。
解鎖時機由留言者本人決定（即時 / 特定日期 / 離世後）。
遺言屬神聖內容,不可被他人篡改 / 誤刪;權限與保存須最高規格審慎。
設計須極溫柔、有尊嚴,杜絕任何輕佻或遊戲化元素。
情感重量最高,列為最需慢慢設計、認真打磨嘅長遠功能,非近期實作。

## [決策] 家庭日曆提醒呈現方式（3.4 情感推送引擎）
- 日期：2026-08-27
- 背景：家庭日曆需要「提前一個月」提醒家人重要日子。核心矛盾——重要日子要一定睇得到，但唔可以令 app 感覺煩／迫，尤其忌辰場合。
- 決策（按時間遠近分層）：
  1. **遠期（約一個月前）**：出現喺家庭圈 feed，溫和，自然引導家人留言祝福，唔打斷用戶。
  2. **迫近（0–3 日／當日）**：入 app 時彈出卡，提供一個行動窗口（一鍵祝福／意向按鈕）。紀律：只有迫近日子先觸發彈出卡，避免長者反射式撳走而令功能失效。
  3. **首頁 banner（本月概覽）**：v1 延後，可選，非必要。
  4. **忌辰特別規則**：永不彈出。只用安靜、莊重嘅 feed 提示，零商業意圖（只容許鮮花／拜祭意向，不可訂蛋糕／餐廳等）。
- Out of Scope（mockup 階段做唔到，待後端／狀態管理）：
  - 彈出卡嘅觸發邏輯：撳走記憶（今日已顯示）、只行動一次、迫近日子判斷。
  - 靜態 mockup 可展示彈出卡外觀去核對設計，但觸發邏輯屬 backlog。
- 待辦：之後需為「feed 提示卡」及「入 app 彈出卡」寫 design spec（參照 B2／B3／B4 流程），包括一般版 vs 忌辰莊重版樣式。

## [決策] 提醒卡流程 + 事件詳情頁（3.4 情感推送引擎）
- 日期：2026-08-27
- 背景：NBP 設計提醒卡時新增咗「事件詳情頁」畫面，解決 feed 卡／彈出卡地方細、擺唔落太多行動選項嘅問題。經確認採用此結構。
- 完整流程：
  提醒卡（feed 版 A 或入 app 彈出版 B）→ 撳「去安排」→ 事件詳情頁（集中所有行動）
- Feed 卡兩個掣邏輯（已定）：
  1. **「送上祝福」** = 輕量，當場直接喺 feed 留言祝福，不入事件詳情頁。理由：長者即興表達關心，一撳即得，符合零學習成本。
  2. **「去安排」** = 入事件詳情頁，做認真、需要空間嘅安排。理由：訂禮物／搞聚會／邀請投票唔係一句話搞掂，需要獨立空間。
  - 兩條路不重複：送祝福喺 feed 解決，去安排喺詳情頁解決。
- 事件詳情頁組成：
  - 頂部：事件對象 + 日期（例：陳大文 的生日、10 月 15 日）
  - 中間「可以為他做什麼？」三個大掣：送上祝福（電子賀卡／語音）、去安排（禮物／聚會／活動）→ 連去家庭聚會 tab、邀請其他家庭成員
  - 下半部「大家的祝福」：集中顯示已留低嘅祝福
  - 詳情頁內亦有「送上祝福」掣（俾已入頁嘅人用），與 feed 卡快捷入口不矛盾，同功能兩個入口。
- 忌辰版事件詳情頁（特別規則）：
  - 「可以為他做什麼」三個掣須換成莊重版，只可「獻上思念／送上鮮花」等
  - 嚴禁禮物、聚會、慶祝類或任何商業按鈕，與提醒卡忌辰版（版本 C）一致
- Out of Scope（mockup 階段做靜態外觀，功能待後端／狀態管理）：
  - 事件詳情頁「大家的祝福」實際留言資料
  - 三個行動連去唔同地方嘅實際跳轉邏輯
  - 邀請成員、投票等多人互動
- 備註：家庭圈新版設計（NBP 出圖）較 repo 現版明顯精緻，已納入考慮採用，待 NBP 寫 detail design prompt 時一併處理。

## [決策] 相簿配額改為「每樹顯示位」+ 相片私隱可見性（v2 修訂）

- 日期：2026-09-01
- 背景：初版「配額計主人、全 app 一個相簿、5+2 綁人」未有考慮「一人屬多棵樹」嘅真實情況（如父母離婚再婚，子女同屬父樹與母樹）。成員需要就「同一張相是否畀不同樹嘅家人睇」行使私隱選擇——此為以「一個真實嘅人」角度出發之合理需求。
- 決策：
  1. **配額改為「每樹顯示位」**：每位成員於每一棵所屬樹，每月各有 5 相 + 2 片顯示位。每棵樹恆封頂 5+2。
  2. **共用相如實佔格，不倍增配額**：一張相／片擺 N 棵樹即佔該 N 棵樹各一格，不能靠同時擺多樹憑空取額。例：一成員屬父樹與母樹，上傳 3 張共用相（兩樹各扣 3），再各擺 2 張私相入父／母樹 → 實際上傳 7 張，父樹母樹各顯示 5 張。
  3. **本人總相簿範圍**：成員本人可睇到自己上傳嘅全部。其總量介乎 5+2（全部共用）至 N×（5+2）（全部私擺，N = 所屬樹數）。此為多樹之自然結果，非增值。
  4. **相片私隱（可見性）綁「人 × 樹」**：每張相／片記錄「喺邊啲樹可見」。可見性係成員私隱權，系統底層保留完整記錄，由成員自行決定畀邊棵樹家人睇。
  5. **單次上傳、只儲一份不變**：承 Core Document 3.2「單次上傳、多處呈現」，只儲一份檔；可見性以顯示位／標籤表達，不重複儲存。
  6. **上傳時揀樹 + 記住預設**：上傳可揀擺邊棵樹（可全選 = 各樹一致，或逐棵揀），系統記住上次選擇作預設，減長者操作負擔。
  7. **本人自睇 = 全部**：成員本人永遠睇到自己全部相片（跨所有樹）；私隱可見性只對其他家人生效。解答「若可上傳多套，本人如何檢視自己相簿」——本人一律睇全部。
  8. ~~**成長相簿同理**：成長相簿（新生嬰兒／新寵物）之額外 5+2 亦採「每樹顯示位」+ 可見性模型，與成員相簿分開計。~~ **（已由 v1.6 修訂／取消：成長相簿一律每位成員一個，不另設 BB／寵物專屬相簿或額外配額。見下方 [決策]。）**
  9. **增值收費 = per tree 升級，非買總額**：多棵樹自然多額，屬正常結構，不收費。增值收費僅針對「單一棵樹想要更高每月額」（如某樹 5+2 → 10+4）。收費 UI／金流仍屬 out of scope（承 rules.md 第 12 條）。
  10. **設計為大多數優化**：複雜情況（多重婚姻、多樹、逐樹私隱）系統必須支援得到（裝得落），但介面預設須為大多數簡單家庭優化，不得因少數複雜情況令一般用戶覺得繁複。
- Out of Scope（仍不做）：跨家庭無限世系探索；細至個別家人嘅權限（可見性只做「逐樹顯示位」層級）；顯示／隱藏濾鏡進階 UI（v2+）；收費介面／金流。

## [決策] 關係模型正式定為 Edge-based + 記錄層／顯示層分離（v2 修訂）

- 日期：2026-09-01
- 背景：初版雖已於 Core Document 3.1 提出「edge-based（邊為本）、以觀看者角度呈現」，但未展開處理真實家庭嘅複雜關係。實際情況包括：多重婚姻（如成員之姊結婚兩次、其配偶結婚三次）、離婚後再婚、繼親、領養、前配偶各自另組家庭等。初版亦未釐清「系統記錄嘅真相」與「用戶想顯示嘅樹」兩者之分別。本決策予以補全。
- 決策：
  1. **關係為獨立嘅「邊（edge）」，不塞入成員節點。** 成員（人／寵物）為節點（node）；夫妻、親子、寵物—主人等關係為獨立記錄嘅邊。嚴禁以 parent_id／spouse_of 等單一指針塞入成員記錄嚟表達關係——該做法無法承載多重婚姻與多家庭，已明確棄用。
  2. **關係邊須帶類型與狀態。** 親子邊帶 relation_type（血緣 biological／領養 adopted／繼親 step）；婚姻邊帶 status（現任 current／離婚 divorced／喪偶 widowed／分居 separated）及可空之 start_date／end_date。
  3. **一人可有多條同類邊。** 一個人可有多條婚姻邊（對應多段婚姻）、可屬多個家庭。系統對邊之數量不設人為上限。
  4. **記錄層 vs 顯示層，嚴格分離（核心原則）。** 系統底層記錄所有真實關係，完整無缺（記錄層 = 真相）。用戶睇到嘅樹，係按「觀看者角度」+ 用戶之顯示選擇呈現（顯示層 = 濾鏡）。顯示層之隱藏／篩選，永不刪除記錄層之真相。
  5. **以觀看者角度呈現（承 Core Document 3.1）。** 同一個人喺唔同家庭／唔同觀看者眼中，位置與呈現可以不同。例：父母離婚各自再婚，子女同時屬父樹與母樹；父樹只呈現父之現任家庭（不顯示前妻），母樹只呈現母之現任家庭（不顯示前夫），而子女於兩樹皆出現。前配偶「不顯示」= 佢不屬該顯示範圍，而非從記錄層刪除。
  6. **離婚／再婚／繼親／領養之處理方式：**
     - 離婚：婚姻邊 status = divorced，親子邊不變（生父母恆定）。
     - 再婚：新增一條 status = current 之婚姻邊；繼父母透過父母之新婚姻邊自然帶出，不另設欄位。
     - 繼親：透過父母之新配偶關係呈現；如需標記，親子邊 relation_type = step。
     - 領養：親子邊 relation_type = adopted，指向養父母。生父母如需保留，v1 先以簡化方式處理（必要時 v2 另設生父母邊）；多數家庭簡化版已足。
  7. **世代推移與離世，一律家人手動輸入觸發（承 rules.md 第 17 條、本文件第六節）。** 系統絕不自行推斷離世或更動世代。
  8. **多家庭切換（承 Core Document 3.1、六）。** 屬多個家庭之成員，提供家庭切換元件；只屬單一家庭則自動隱藏，保持簡潔。切換樹時，一併載入該樹對應之成員排位與相簿顯示位（呼應上一決策之「每樹顯示位」）。
- Out of Scope（仍不做，承 Core Document 第八節）：跨家庭無限世系探索；自動稱謂推算（智能關係計算）；細至個別家人之權限；顯示／隱藏濾鏡之進階 UI（v2+）。v1 顯示層只做「家庭之間切換」+ 基本親子／婚姻呈現。

## [待議 / Backlog] 樹內可見範圍與遠親私隱（承 v1.3、v1.4 之延伸缺口）

- 日期：2026-09-06
- 背景：現行私隱決策（v1.3 相片可見性綁「人 × 樹」、v1.4 記錄層／顯示層分離）處理嘅係「同一人喺多棵樹之間，相片畀邊棵樹睇」。但家庭樹會隨邀請自然生長，一棵樹內可能出現大量遠房親戚。產品負責人提出新顧慮：同一棵樹之內，遠近親疏之間嘅可見範圍未有處理——用戶未必想啱啱加入嘅遠房親戚睇到自己嘅相片、生日、個人資料。此為 Core Document 第八節「第一版只做簡易預設：直系相連家人可見／複雜權限 out of scope」所刻意留低嘅缺口。
- 現狀（v1 行為，已定）：v1 只做簡易預設「直系相連家人可見」，全樹成員一律可見，不設樹內分層權限。此條目不改變 v1，僅記錄將來 SSO／多用戶落實時需處理之議題。
- 觸發時機：待 SSO／多用戶帳號系統落實、一棵樹真正出現多帳號活躍成員時，方需正式設計。單一家庭、成員相互熟悉之階段暫不需要。
- 待拍板問題（將來 spec 階段）：
  1. 可見性單位：以「直系／旁系距離」（如 N 代以內可見）為單位，定係「用戶逐個／逐群手動批准可見」？後者對長者可能過於複雜，須權衡。
  2. 預設值：新加入之遠親，預設可見定預設受限？依產品「為大多數簡單家庭優化」原則（v1.3 第 10 點），傾向預設簡單、進階選項收埋。
  3. 保護對象範圍：相片、生日、個人資料三者是否同一套可見性，抑或分開（如生日可全樹見、相片限親近）？
  4. 加入遠親時之同意機制：被加入者是否需確認、或收通知？呼應 Core Document「私密為先」信念。
  5. 已離世成員：先人相片對全樹之懷念價值（承第五節、第六節願景）與私隱之平衡——離世成員資料之可見範圍是否另有規則。
- Out of Scope（明確不做，承 Core Document 第八節）：v1 不實作任何樹內分層權限；不做細至個別家人之逐一權限 UI（v1.3／v1.4 已列此為 v2+）。本條目僅為 backlog 記錄，不觸發任何 v1 開發。
- 與現有決策之關係：本條目係 v1.3（人 × 樹可見性）、v1.4（記錄層／顯示層分離）之延伸，方向一致——底層記錄完整、可見性為顯示層濾鏡；差別僅在本條目聚焦「樹內遠近」而非「樹與樹之間」。將來實作須沿用同一套「記錄層保留、顯示層濾鏡」模型，不得另起爐灶。

## [決策] 商戶廣告收入模式（釐清第四節「不向商戶抽佣」）

- 日期：2026-09-06
- 背景：第四節【已定】原有「不向商戶抽佣」一句，易被誤解為「平台不向商戶收取任何費用」。本決策予以釐清：該句僅指「不抽取交易佣金」，不排除廣告／上架收入。商戶廣告費為平台之主要收入來源。
- 決策：
  1. **廣告／上架收入為平台認可之主要收入來源。** 所有出現於 app 之商戶，一律須先付「上架費」方會出現（未付＝不存在於 app）。此為 `is_listed` 概念。
  2. **廣告費影響排序與呈現豐富度。** 已上架商戶之間，付費較多者可購買更前排位、圖＋片豐富呈現、贊助位。此為 `ad_tier` 概念。
  3. **不抽佣（維持第四節原則）。** 平台不於商戶單筆交易中抽取佣金（commission）；廣告／上架費與商戶是否成交無關，屬固定曝光費用。「不抽佣」與「收廣告費」並存不悖。
  4. **收費對象與流程。** 廣告／上架費僅涉「商戶與平台之間」，不涉及用戶付費、不涉及 app 內金流。v1 以線下方式向商戶收費，後台僅設定該商戶之付費狀態（`is_listed`）與廣告等級（`ad_tier`），不建任何 app 內支付流程。
  5. **贊助標示（用戶信任底線）。** 凡付費取得之排前／贊助位商戶，UI 須清楚標示「贊助」或「推廣」字樣，不得偽裝為中立推薦。此為向商戶收費模式下保障長者用戶信任之底線，不可省略。
  6. **與第四節之關係。** 本決策為第四節「商業模式」之補充與釐清，非推翻。第四節「只為老有樹自家服務向用戶收費（Freemium）」之定位維持不變；本決策新增「商戶付費廣告」為第二條收入線，兩者並存：用戶端 Freemium、商戶端廣告費。
- Out of Scope（v1 不做）：app 內支付／金流；向商戶抽取交易佣金；用戶付費解鎖商戶內容；商戶自助後台（v1 商戶資料與付費狀態由平台內部設定）。

## [決策] 家庭聚會協作正式落地：發起 → 候選 → 逐人投票 → 確認 → 邀請卡（2026-09-10）

- 背景：v1.8 只交付「場合 → 商戶」瀏覽。實際使用需要嘅係**真正安排一個聚會**：爸爸生日將到 → 撳「去安排」→ 發起聚會 → 揀餐廳（一個直接確認，或幾個畀家人投票）／訂蛋糕（揀商戶＋取貨地點時間）／買禮物（建議清單）→ 確認 → 通知家人。原規格將「逐人投票／RSVP」列階段二（待 SSO）；但 per-member 登入（`member_auth` + `family_session` + `getCurrentMember`）已於較早交付，每位家人各自有身份，**階段二之前置條件已消失**，故一併落地。
- 決策：
  1. **三表落地**（migration 0015）：`gathering`（聚會主體：場合／對象／標題／目標日期／狀態／邀請卡 id）、`gathering_option`（候選項：`kind`＝date／place／cake／gift、商戶、日期時間、取貨地點、**負責人**、狀態）、`gathering_vote`（逐人投票：每人每項一票，`UNIQUE(option_id, voter)`，可改／可收回）。
  2. **一個聚會可同時有多個項目類別**：地點 ＋ 蛋糕 ＋ 禮物 ＋ 日期並存，各自可有 1..N 個候選。
  3. **唯一性**：`date`／`place` 確認一項時，同類其他候選自動「落選」（一個聚會只有一個日子、一個地點）；`cake`／`gift` 可確認多項。
  4. **確認聚會 → 自動生成家庭圈邀請卡**（承 spec §5.2）：內容由已確認候選組合（標題／日期／地點／蛋糕取貨／禮物），並用已確認地點商戶相片作封面；取消或刪除聚會會一併清走該貼文。
  5. **入口**：提醒卡「去安排」→ `#/family-gather?plan=1&occasion=&subject=&date=`，自動帶入場合／對象／日期開表單。
  6. **忌辰（莊重場合）：API 層禁止發起聚會**（`occasionAllowed()` 擋，回 400），非只靠前端隱藏按鈕（承 rules §23）；忌辰提醒卡「去安排」只跳去莊重分支（鮮花／拜祭，零廣告）。
  7. **不涉交易**（承第四節）：地點／蛋糕／禮物一律以「候選 + 一鍵致電／WhatsApp／導航」呈現，App 內不落單、不付款、不抽佣。

## [決策] 家庭聚會定位修訂：首頁＝行動中心，商戶只在「需要」時出現（2026-09-10）

- 背景：v1.8／v1.9 首版把「場合 chips ＋ 商戶列表」直接放在家庭聚會首頁，令頁面變成第二個「我的推薦」，與「有目的才需要商戶」的商業模式相反 —— 用戶毫無目的地被推商戶，商戶亦得不到真正有意的客戶。
- 決策：
  1. **家庭圈＝給祝福（情感）；家庭聚會＝採取行動（有目的）**。兩者分工不可互相複製：祝福留在家庭圈，需要幫手才入家庭聚會。
  2. **首頁不再列出商戶目錄**。首頁只有三部分：① **即將到來**（生日／節日／重要日子提醒，一按「去安排」）；② **需要安排什麼？**（快速安排：發起聚會／訂餐廳／訂蛋糕／買禮物／定日子）；③ **我的聚會**。
  3. **商戶只在「需要服務」那刻出現**（`MerchantPicker`）：由 tile／提醒帶入，先按需要過濾類型，並提供 **搜尋、類型（主分類）、標籤（子篩選）、區域／地區、排序（推薦／按地區／按名稱）** 及贊助標示。
  4. **先問「加入哪個聚會／建立新安排」，然後才揀商戶** —— 確保每一次商戶曝光都對應一個真實目的（這就是商戶廣告費的價值來源，強化第五節「商戶廣告收入模式」）。
  5. **需要 → 商戶匹配：標籤優先、主分類後備**。商戶有標籤就用標籤判斷（例：茶餐廳不會出現在「訂蛋糕」）；完全沒有標籤的舊商戶才用主分類後備。
  6. **忌辰**：首頁提醒卡只提供「獻上思念」→ 走莊重分支（只鮮花／拜祭商戶、零廣告、不建立聚會）；API 層亦禁止以忌辰發起聚會（承 v1.9 及 rules §23）。
  7. **新增 `GET /api/merchants-meta`**：回傳地區／類型／標籤篩選選項，且只列出「至少有一個已上架商戶」的選項，避免空篩選。
- Out of Scope（維持）：App 內金流／落單、商戶評分評論、商戶與用戶即時通訊。
- 與其他文件之關係：修訂 `family_gather.md` §2（入口）、§3.2（場景→商戶映射改為「需要 → 標籤優先」）、§4（用戶端功能）。
- 驗證：`scripts/test-merchant-query.mjs` 23/23（類型匹配／搜尋／地區／分類／標籤／排序／忌辰零廣告）；`scripts/test-gathering-e2e.mjs` 30/30；本機 `GET /api/merchants-meta` 6/6。

## [決策] 節日推廣券（雙動作）＋ 商戶資料工具＋聚會通知（2026-09-10）

- 背景：商戶付費推廣要有實際落地位；同時要定義「推廣可以綁咩」。經確認：**推廣係綁「節日」**（例：中秋節訂枱），**唔可以綁個人**（例如某位家人生日）——因為個人生日唔應該商業化，而節日係全家庭共同需求、商戶亦真正有推廣價值。
- 決策：
  1. **推廣必須綁節日（schema 層 NOT NULL）**：新表 `promotion(festival_id NOT NULL)`；`festival` 為節日曆（每年更新一次，日期由產品負責人核實）。 API 亦只接受有節日嘅推廣。
  2. **雙動作，零金流**（承 §6 及 Core Document 第四／八節）：
     ① **領取（Claim）**：平台記錄會員（`promotion_claim`，`UNIQUE(promotion_id, member_no)` 一人一次；`quota_total` 名額原子遞增控管）、
     ② **一鍵 WhatsApp 預約**：帶預填訊息去商戶（商戶自行記錄、線下核銷）。平台不落單、不收款、不抽佣。
  3. **入場方式**：家庭聚會「即將到來」顯示節日 → 一撳「去安排」建立**節日聚會**（`gathering.festival_id`）→ 之後「加入候選（訂餐廳／蛋糕／禮物）」時，商戶清單會顯示**該節日**嘅推廣（可領取）。商戶曝光只喺呢個有目的嘅一刻出現。
  4. **准入與誠信不變**：推廣只限 `is_listed = 1` 商戶；付費排序繼續標示「贊助」；**忌辰零廣告**（rules §23）——忌辰分支永遠唔會載入／顯示推廣。
  5. **商戶資料錄入工具**：新增 `data/merchants.json`（人手編輯）＋ `scripts/generate-merchant-sql.mjs`（驗證 + 產生 UPSERT SQL；**唔會**重設已領取名額）＋ `scripts/generated/merchants.sql`（產物）。檔案內附**示範商戶（名稱標示「示範」、電話用假號碼）**覆蓋蛋糕／鮮花／禮品／酒樓，令各流程即時可用；正式上線前必須換成真實已收費商戶。

## [決策] 推薦獎勵券（Type B）＋ 推薦飛輪落地（2026-09-10）

- 背景：spec §6 已定「統一 coupon engine」兩個 type。v1.11 已落地 Type A（節日推廣券，綁節日）。Type B 係**推薦飛輪**嘅燃料（§8）：長者為攞券而推薦家人 → 家庭樹增長 → 用券去家庭聚會幫襯商戶 → 商戶見真實引流更肯出券／廣告 → 平台有更多更好券 → 更有動力推薦。
- 決策：
  1. **Type B 不綁節日，綁「成功推薦人數」**（`reward.required_referrals`，例：5）。與 Type A 分表（`reward` vs `promotion`）：Type A 因「推廣必須綁節日」而 `festival_id NOT NULL`；Type B 則以推薦解鎖為條件。**兩者共用同一套「雙動作」領取 UX**（平台記錄領取 ＋ 一鍵 WhatsApp 向商戶確認，零金流、不抽佣），前端由同一元件 `CouponSticker` 呈現，避免兩套玩法。
  2. **「成功推薦」＝家人真正加入**（唔係單撳邀請就計）。兩條路徑都會標記 `referral.status = 'joined'`：
     - ① 被邀請人自己完成首次設定（`family/setup.ts` 以電話配對）
     - ② 邀請人喺「加成員」加入該家人（`members.ts` 以電話配對，且屬同一家族）
     即係「派出去嘅邀請」同「真正落地嘅推薦」分開，唔會俾人刷數。
  3. **一人一次、名額有限**：`UNIQUE(reward_id, member_no)`；`quota_total` 用條件式 UPDATE 原子控管（與 Type A 同一手法）。
  4. **私隱**：`GET /api/referrals` 只回傳**遮罩電話**（例 `9333****`）；唔會回傳完整號碼。
  5. **入場方式**：家庭聚會首頁「推薦獎勵」區 —— 顯示進度（已成功推薦 N／5）、一撳記錄邀請並用 WhatsApp 邀請、已邀請／已加入清單、解鎖後可自選商戶優惠券並領取。
  6. **忌辰零廣告**（rules §23）：莊重場合唔會出現任何券（推廣或獎勵）。
  7. **商戶資料工具同步支援**：`data/merchants.json` 加 `rewards[]`（Type B），由 `scripts/generate-merchant-sql.mjs` 一併產生 UPSERT SQL（唔會重設 claimed_count）。
- Out of Scope（維持）：推薦獎賞嘅**現金／積分**（只做商戶券，零金流）、排行榜／裂變獎勵、商戶自助後台、coupon code／QR 核銷自動化。
