# CoAppery 模組化開發 SOP

## 目的

確保用 AI（Genspark Code 等）開發系統時，程式碼以「積木」方式組織，達到三個目標：改一處影響多處、每次修改只需讀一個小檔、降低 token 消耗與 bug 風險。本 SOP 為每次開新頁面或新功能前的固定動作。

---

## 核心原則

系統由三層構成，職責嚴格分離：

**第一層：共用件（shared modules）** —— 跨頁面重複使用的最小單位，例如頂欄、底部導覽列、卡片、上傳面板。放於 /packages，各有獨立 module.json 與 props interface。共用件只靠 props 運作，不得引入業務資料或 mock 陣列。

**第二層：組合件（composite modules）** —— 由多個共用件或元素組成、且會在多處重用的中型組合，例如「一代 section（標題 + 卡 + 指示點）」、「輪播連 peek 卡」、「代與代之間的連接線」。同樣放於 /packages，有自己的 module.json 與 props。

**第三層：頁面檔（page）** —— 只負責「佈局」與「資料」：決定用邊幾個組合件/共用件、擺喺邊、塞咩 data。頁面檔不應包含複雜視覺邏輯或可重用的 UI 片段。

---

## 硬性規則

**規則 A — 開頁前必先做積木分解。** 任何新頁面或新功能開工前，必須先產出一份「積木分解清單」，列明：（1）本頁用到哪些現有 module；（2）需新建哪些 module 及其 props；（3）頁面檔只保留佈局與資料。此清單經人手確認後，方可交 AI 寫 code。

**規則 B — 檔案行數上限。** page 頁面檔 ≤ 200 行、module 組件檔 ≤ 250 行。超過即為訊號，代表有可重用片段應抽成 module，須停低拆分。此為警示線而非死線；若有合理原因超出，須經 owner 確認並於 build log 記錄原因。

**規則 C — 修改前先定位所屬 module。** 修改任何細節前，先判斷「呢個 fix 屬邊個 module」，只開嗰個 module 交 AI 處理，不得將整頁掉俾 AI。此為控制 token 與避免波及其他部分的關鍵。

**規則 D — 共用件一改全域生效。** 需要調整共用件行為時，直接改嗰個 module；嚴禁喺 page 檔內 copy 一份再改，否則失去模組化意義並製造分歧。

**規則 E — module 邊界清晰、單向依賴。** 共用件不得反向 import page 或業務資料；組合件可 import 共用件；page 可 import 兩者。依賴方向永遠由上（page）向下（module），不可逆。

**規則 F — 每個 module 必須有 module.json。** 記錄 name、label、category、version、dependencies、derivedFrom（來源設計/規範章節）、docs。確保每塊積木可追溯到設計文件。

---

## 標準流程（每次開新頁）

**第一步，積木分解：** 由負責人（人 + AI 助手）對照設計文件，產出積木分解清單，區分「重用現有」「新建」「頁面佈局」三類。

**第二步，確認清單：** 人手 review 清單，確認邊界合理（冇一個 module 過肥、冇本應共用嘅嘢寫死喺 page）。

**第三步，寫 module（如有新建）：** 先起新 module 並各自 build 通過，再砌 page。可分兩個 commit（先 module 後 page）以降低風險。

**第四步，砌 page：** page 檔只做 import + 佈局 + 塞 data，控制喺 200 行內。

**第五步，驗證：** grep 檢查（硬編色、禁用字等）、npm run build 零錯誤、props interface 向下相容、build log 依規則記錄、deploy preview 肉眼核實視覺。

**第六步，修改時：** 依規則 C，只開所屬 module。

---

## 與現有規範的關係

本 SOP 與 rules.md 並行：rules.md 管內容與語體（色彩、字級、語言、child safety 等），本 SOP 管程式碼結構。兩者衝突時，以較嚴格者為準。

---

## 修訂機制

本 SOP 為活文件。實戰中若發現規則過緊（阻礙開發）或過鬆（擋不住 bug），應予修訂。修訂由對話助手產出修訂 prompt、更新本文件、記入 build log，並於下方「修訂記錄」表補一行（日期 / 修改內容 / 原因）。
